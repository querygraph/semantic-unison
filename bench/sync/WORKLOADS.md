# Additional SOL workload recipes

`workloads.py` is a pure generated-container recipe library. It opens no path,
creates no fixture, executes no Unison process and grants no IO. The existing
`fixtures.py`, frozen cohorts and their completed result bytes are unchanged.

Its synthetic Classic TIFF header declares distinct primary encoded payload,
JPEG-interchange preview, XMP and complete remaining opaque bytes. Payloads are
arbitrary, not valid photographic encodings or SDK qualification inputs.

| Recipe | Independent byte effect | Expected path, not an observed result |
| --- | --- | --- |
| fixed-xmp | Same-sized packet replacement only | SDE-eligible generated shape |
| growing-xmp | Increase packet size, append new packet, update count+pointer; preserve every old payload byte | Exact fallback because extent/size changes |
| metadata-preview | Replace XMP and XOR one declared preview byte | Exact fallback because protected complement changes |
| metadata-raw | Replace XMP and XOR one primary encoded byte | Exact fallback because protected complement changes |
| metadata-opaque | Replace XMP and XOR one unclaimed gap byte | Exact fallback because protected complement changes |
| full-change | Stream XOR255 over every source byte in bounded1MiB chunks; same output length | Exact fallback; no declared image validity |
| malformed-ifd | Replace XMP and point the firstIFD beyond EOF | Parser refusal/ordinary exact fallback expected |
| unsupported-signature | Replace XMP and change TIFF byte-order signature toNO | Unsupported-container ordinary exact fallback expected |

`initial_writes(layout)` overlays a separately streamed deterministic noise
source. `recipe(layout, kind)` returns immutable, nonoverlapping byte actions and
an exact target size. XOR actions require reading only that generated byte.
No receiving clone, in-place editor for real TIFFs, or general TIFF serializer
is supplied. The consumer owns all source/destination paths, permits and hashes.

Six original in-memory controls independently decode the header and check exact
changed-byte sets, append geometry, preservation, bounds and forged contracts.
They are not parser acceptance tests or timings. See
`tests/qualification/generated-workload-recipes-actual-20261019.json`.

## Next integration and outstanding workloads

The benchmark runner now consumes non-fixed recipes through `--workload`.
`fixed-xmp` retains the original generator/bytes; the added preview-capable
container is used only for new scenarios. The new owned consumer creates0600
exclusive generated files, guards identity/digest before editing and uses
qualified one-shot descriptor closes. The runner independently hashes final
donor/received files, preserves the old basis and verifies no-op receiver inodes.
New workloads refuse legacy partition/qualification controls; fresh versioned
source-qualified IO plans and actual Unison execution remain required.
Source/target sizes are recorded separately and capacity uses the larger extent. Strict SDE
success expectations must remain for fixed-XMP cohorts; fallback workloads must
be reported as fallback, never silently counted as semantic acceleration.

No-change/new-file, thousands of small files, mixed malformed/unsupported
corpora, concurrent editor and mostly eligible mixed corpus
still require their corresponding workload designs/execution. Same/cross-volume,
non-APFS and actual network/cold-cache scopes remain separate. At least five
measured repetitions after declared warmups remain the SOL benchmark contract.
Larger sizes alone do not replace these workloads. Do not start any IO until the
current Photo window is released and the new exact owned run is coordinated.

## Current source integration evidence

Fourteen tiny recipe/owned-file/counter controls passed, including close
uncertainty (original carrier preserved/no numeric retry), alias/replacement
refusal and independent changed-byte oracles. Legacy fixed/layout fixtures and
actualCLIhelp passed separately. Two actualCLIpreexec guards refused insertion
into frozen partition/qualification runs without creating output or executing
the supplied inert binary. See
`tests/qualification/generated-workload-integration-actual-20261019.json`.
No Unison sync or benchmark was run; fallback expectations are still predictions
until the separately coordinated native qualification. No SDK/Photo data used.

Full-change and the two malformed/unsupported recipes now have directed tiny
consumer controls in addition to the earlier five recipes. The complete15-test
source suite passed, as did legacy fixture and actualCLIhelp checks; see
`tests/qualification/generated-workload-extended-actual-20261019.json`.
All eight recipes still await their actual Unison receiving/benchmark execution;
a passing generator does not prove expected fallback or transfer correctness.

Every current recipe declares a change. The consumer and runner now both reject
an unchanged before/after SHA before update measurement. A deliberately empty
recipe is an injected negative control: it must fail and cannot become a fast
"full-change" no-op sample. Sixteen tiny source controls passed; actual receiving
still remains unstarted. No-change measurements use their separately reported
saved no-op calls, not this change-only recipe interface.

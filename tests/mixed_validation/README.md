# Mixed validator, metadata helper and worker control

`probe.ml` links the current compiler-matched production runtime, validator,
external-helper bridge and worker implementations. It starts one require-mode
validator, one metadata request and sixteen hashes in the same six-credit
scheduler, then waits for every captured task result. It records SDK process/
group/wait/raw-protocol evidence and generic external-process diagnostics before
checking candidate fences and settled CPU/child/worker/FD state. No publication
or semantic optimization is performed by this harness.

`run_controls.py --build-result PATH --report NEW_PATH` builds that probe and
runs four original fake-only combinations: both succeed, validator errors with
exit0, metadata exit7, and both findings. Its only helper executables are authored
inside its private workspace. It binds each recorded helper PID to that fake's
independent call ledger, checks exact protocol bytes and expected acceptance,
checks the complete owner closure record and unchanged candidate hash/eight-field
epoch, and retains unknown process evidence rather than interpreting it as an
ordinary failed-prefix release. The build prefix and native objects are pinned.

## Independent task and failed-prefix audit

`audit.py` reconstructs exact launch/candidate/build bindings, parses the SDK
process/group/raw protocol, joins the single metadata helper record and compares
final owner/counter claims. A valid raw frame with errors remains a functional
failure despite exit0. Metadata exit0 is separate from JSON source/version
verification; exact decimal version spelling is preserved. Unknown process
states, missing/duplicate records, helper identity/cost contradictions and
truncated owner capture refuse. Historical PID text is not authenticated by
being parseable, and no audit result authorizes FD/resource release.

`audit_prefix` distinguishes complete two-probe results, a known failed prefix,
pre-call failure and a possibly started invocation with missing outcome. It
rejects continued work after a failed case and never promotes a failed overall
result merely because its attempted tasks settled. Independent parent terminal,
worker reap, source/tool/input pins and held resource closure are caller duties.

## Callable journal worker

`worker.py` runs exactly two caller-pinned probes serially. It persists a detached
INTENT before invocation and the raw OUTCOME before auditing or checking input
fences. A failed first probe prevents the successor; insufficient deadline
headroom prevents preparation/launch. Publication errors become retained
ownership uncertainty, and existing uncertainty carriers propagate unchanged.
The worker never releases resource descriptors. Its callback contract requires
the caller to provide pinned preparation, invocation, source and input checks.
